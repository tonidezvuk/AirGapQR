# AirGapQR Protocol

This document describes the transfer protocol used by AirGapQR v0.5.0.

The implementation in `protocol.py` remains the authoritative reference for protocol behavior.

## Overview

AirGapQR transfers files between isolated systems using a sequence of QR codes.

The basic transport model is:

**FILE → QR FRAMES → OPTICAL CHANNEL → QR FRAMES → FILE**

No network connection is required between the sending and receiving systems.

A source file is divided into payload chunks. Each chunk is encoded into an AirGapQR protocol frame and displayed as a QR code.

The receiving system collects valid frames, reconstructs the original byte sequence, and verifies the resulting file using SHA-256.

## Current protocol version

AirGapQR application version:

**v0.5.0**

The current default payload chunk size is:

**100 bytes per QR frame**

The protocol currently supports files up to:

**5 MiB**

## Transfer structure

A transfer contains metadata describing the file and a sequence of indexed payload frames.

Protocol frames contain the information required to associate a QR frame with a particular transfer and reconstruct the original file in the correct order.

The protocol includes information used for:

- transfer identification
- frame indexing
- total frame count
- file metadata
- file-size validation
- source SHA-256 verification
- payload integrity checking
- payload reconstruction

The exact protocol field definitions are implemented in `protocol.py`.

## Transfer ID

Each transfer uses a transfer identifier generated by AirGapQR.

In v0.5.0 a valid transfer ID must be:

- exactly 16 characters
- lowercase hexadecimal

Frames from another transfer must not be silently accepted into the active transfer.

## Frame indexing

Each payload frame has an index.

The receiver uses frame indexes to:

- place payload data in the correct order
- identify already received frames
- detect duplicate frames
- identify missing frames
- reconstruct the original file

The total number of frames is bounded by the protocol implementation.

## Payload encoding

Binary file data is transported through QR-compatible protocol text.

AirGapQR applies limits to:

- decoded payload size
- Base64 payload length
- total protocol frame text size

Oversized protocol inputs are rejected.

## File-size limit

AirGapQR v0.5.0 limits the declared file size to:

**5 MiB**

The receiver also tracks the amount of payload data accepted during a transfer.

The total number of received payload bytes cannot exceed the file size declared by the transfer metadata.

## SHA-256

The source file SHA-256 value is included in transfer metadata.

A valid SHA-256 field must contain:

- exactly 64 characters
- lowercase hexadecimal characters only

After all required frames have been collected, AirGapQR reconstructs the file and calculates its SHA-256.

The RECEIVE interface displays:

**SOURCE SHA-256**

and:

**RECEIVED SHA-256**

A matching SHA-256 verifies that the reconstructed bytes match the hash declared in the transfer metadata.

SHA-256 does **not** authenticate the identity of the sender.

## CRC32

Individual QR payloads use CRC32 for corruption detection.

A valid CRC32 field must contain:

- exactly 8 characters
- lowercase hexadecimal characters only

Frames with invalid CRC32 data are rejected.

CRC32 is intended to detect accidental payload corruption.

CRC32 is **not** an authentication mechanism and should not be treated as cryptographic integrity protection.

## JSON validation

Incoming protocol data must contain valid JSON.

AirGapQR v0.5.0 requires protocol input to:

- decode as valid JSON
- contain a JSON object
- contain the expected AirGapQR protocol fields
- use the expected data type for every field

Unexpected or malformed protocol structures are rejected.

## Strict field types

Protocol field types are validated explicitly.

For example:

- string fields must be strings
- integer fields must be integers
- boolean values cannot silently pass as integer protocol values

This prevents loosely typed JSON values from being interpreted as valid protocol metadata.

## First-frame validation

The first frame received for a transfer receives full validation before its metadata is allowed to initialize receiver state.

A malformed or corrupted first frame therefore cannot lock the receiver into an invalid transfer.

Only validated metadata can initialize a new transfer.

## Duplicate frames

Duplicate frames are handled according to their payload.

### Identical duplicate

If a frame with an already received index contains the same payload data, it is treated as a harmless duplicate.

The existing frame remains valid.

### Conflicting duplicate

If a frame uses an already received index but contains different payload data, the frame is rejected as a conflicting duplicate.

A later frame cannot silently replace previously accepted data for the same frame index.

## Empty payloads

Empty payload frames are rejected for non-empty files.

This prevents malformed frames from being accepted as valid data-bearing frames.

## Missing frames

The receiver tracks which frame indexes have been successfully collected.

If a transfer is incomplete, the RECEIVE interface reports the exact missing frame numbers.

Example:

```text
MISSING FRAMES

17, 43, 88
```

The sender can then retransmit only those frames using:

```text
PLAY SELECTED
```

Normal full-sequence playback can be restored using:

```text
PLAY ALL
```

Missing-frame recovery does not change the underlying transfer metadata.

## Frame ordering

Frames do not need to arrive in numerical order.

The receiver identifies frames by their indexes and reconstructs the file only after the required frame set has been collected.

This allows:

- repeated QR playback
- recovery of individual missing frames
- imported QR images
- duplicate frame reception

without requiring a perfectly ordered optical stream.

## QR decoding

Live camera frames and imported QR images use the same decoding pipeline.

AirGapQR first attempts normal QR decoding.

If normal decoding fails, a perspective-corrected fallback may be attempted.

QR image processing is separate from protocol validation.

Successfully decoding QR text does not automatically make that protocol frame valid.

The decoded data must still pass protocol validation.

## Sender-side validation

Validation is also performed before a transfer is generated.

AirGapQR v0.5.0 validates:

- filename
- input data type
- file size
- configured chunk size
- resulting frame count

Invalid transfer parameters are rejected before QR frames are generated.

## Receiver state

The receiver maintains state only for validated transfer data.

Received frames are accumulated by frame index until the transfer is complete.

Receiver state includes information required for:

- transfer identification
- metadata validation
- frame collection
- missing-frame reporting
- byte-count enforcement
- final reconstruction
- SHA-256 verification

`CLEAR ALL` resets the active receive and recovery state.

## Security properties and limitations

The AirGapQR protocol is designed primarily for offline optical transport and corruption detection.

It provides:

- structured protocol validation
- per-frame accidental corruption detection
- file reconstruction integrity verification
- duplicate conflict detection
- bounded resource inputs

It does not provide sender authentication.

A valid AirGapQR transfer does not prove who created the transferred file.

A valid transfer also does not prove that the transferred file itself is safe to open.

AirGapQR does not execute received files.

## Protocol compatibility

Changes to protocol behavior should be treated carefully.

Future protocol changes should document:

- modified fields
- modified validation rules
- new limits
- compatibility implications
- migration behavior where applicable
- corresponding regression tests

Protocol behavior should not be changed silently.

## Testing

The v0.5.0 protocol regression tests cover behavior including:

- normal encode/decode round trip
- complete file reconstruction
- identical duplicate frames
- conflicting duplicate frames
- corrupted CRC32
- oversized payloads
- malformed JSON
- invalid protocol field types
- oversized file declarations

The current v0.5.0 protocol regression test suite passes.

The test implementation is available in:

```text
test_protocol.py
```
